# 연동함수 그래프 학습 앱 — 설계 문서

날짜: 2026-08-29

## 배경 & 목표

수능 함수 문제 중 "교점 개수 함수", "도함수-원함수 연동", "정적분으로 정의된 함수" 같은 유형은 원함수 그래프와 파생 함수 그래프를 동시에, 인터랙티브하게 보면서 이해하는 게 핵심이다. 기존 계산기(GeoGebra 등)는 범용이라 이런 학습 목적의 "두 그래프를 나란히 두고 값 하나(t)로 연동시켜 관찰"하는 워크플로우에 최적화돼 있지 않다.

목표: 문제 사진을 넣으면(LLM을 통해) 또는 직접 손으로 그려서 원함수/연동함수를 빠르게 입력하고, 슬라이더로 값을 움직이며 두 그래프가 실시간으로 연동되는 걸 눈으로 확인하는 웹 앱을 만든다.

## 전체 아키텍처

- **스택**: React + Vite, 서버 없음(정적 호스팅 — GitHub Pages/Vercel), math.js(수식 파싱/평가), Canvas 2D 직접 구현 렌더링 엔진, CodeMirror(수식 입력 하이라이팅/자동완성).
- **레이아웃**: 좌우 2패널(원함수 / 연동함수)이 기본, 각 패널 하단에 수식 입력창 + 대수뷰(정의된 객체 목록). 두 패널 아래 공유 LinkBar(t 값/동기화 상태).
  - 넓은 화면(≥768px): 좌우 배치
  - 좁은 화면(모바일 세로): 세로 스택으로 자동 전환 (CSS flex-direction 미디어쿼리)
- **상태 관리**: 가벼운 전역 스토어(Zustand 등)로 `t`, 각 패널의 함수 정의(JSON), 파라미터 슬라이더 값들을 공유.
- **함수 표현**: 모든 함수는 내부 JSON 스키마로 표현. math.js는 각 조각의 수식 문자열 평가에만 사용. 입력 방식(타이핑/LLM출력/손그림 인식)에 관계없이 최종적으로 이 스키마로 수렴시켜, GraphCanvas가 입력 출처를 몰라도 되게 한다.

```json
{
  "type": "piecewise",
  "pieces": [
    { "expr": "2*x^3-6*x+1", "domain": [null, 2], "closedAt": { "left": null, "right": true } },
    { "expr": "a*(x-2)*(x-b)+9", "domain": [2, null], "closedAt": { "left": false, "right": null } }
  ]
}
```

## 코어 모듈 (UI와 분리된 순수 로직)

- `mathEngine.js` — math.js 래핑, 커스텀 함수(`piecewise`, `abs`, `min`, `max`) 등록
- `functionSchema.js` — 위 JSON 스키마 검증/정규화
- `rootFinder.js` — `f(x) - t`를 도메인별로 샘플링 후 부호변화 구간을 이분법으로 정밀화하여 실근 개수/좌표 계산 (`solution_count`의 실제 구현체). 다항식 해석적 풀이 대신 수치적 방법을 쓰는 이유: 사용자가 임의 함수를 넣을 수 있어야 범용적으로 안전함.
- `viewport.js` — world↔screen 좌표 변환, 줌/팬 상태, "보기 좋은" 격자 간격(1,2,5,10...) 자동 계산
- `canvasRenderer.js` — 순수 드로잉 함수(축, 격자, 곡선, 열린/닫힌점 마커, 드래그 가능한 `y=t` 선)

## 컴포넌트 트리

```
App (전역 상태: t, leftFuncDef, rightMode, params)
├── MainRow/Column (반응형 컨테이너)
│   ├── Panel (Left)  — GraphCanvas + ObjectList + EquationInput + ParamSliders
│   └── Panel (Right) — GraphCanvas + ObjectList(읽기전용, h(t) 자동계산)
└── LinkBar (t 값 표시 + 연동 안내)
```

## 지오지브라 참고 UX 요소

- **대수뷰**: 각 패널에 정의된 객체 리스트(수식 + 곡선과 동일 색 스와치 + 표시/숨김 눈 아이콘 + 삭제)
- **미정의 문자 → 슬라이더 자동생성**: 수식 파싱 시 `x`/`t` 외의 자유 변수(예: `a`, `b`)를 감지하면 자동으로 파라미터 슬라이더 생성. 문제의 미지수를 실험적으로 조작하는 데 활용.
- **입력창 자동완성/하이라이팅**: CodeMirror로 함수명 자동완성, 괄호 자동 닫힘, 구문 하이라이팅. LaTeX WYSIWYG 렌더링(MathQuill류)은 비용 대비 우선순위가 낮아 MVP 이후로 보류(YAGNI).
- **줌/팬/툴바**: 스크롤/핀치 줌, 드래그 팬, 홈 버튼으로 초기 뷰 복귀. 툴바는 최소화(기본 모드=이동).

## Phase 1 — 그래프 엔진 + 슬라이더 연동 (핵심, 최우선)

**t 연동 상호작용**: Left 패널에 `y=t` 수평선을 그리고 드래그하면 전역 `t` 갱신. Right 패널은 `t`를 구독해 `rootFinder`로 `h(t)`(교점 개수)를 계산, `(t, h(t))` 점을 표시. "Trace On" 토글 시 지나온 점들을 흐릿하게 남겨 함수 개형이 그려지는 걸 시각적으로 보여줌.

**빌드 순서** (각 단계가 독립적으로 눈으로 검증 가능):
1. Vite+React 스캐폴딩, 반응형 레이아웃 껍데기
2. viewport + canvasRenderer: 축/격자 렌더, 줌/팬
3. mathEngine으로 단일 수식 파싱→plot
4. piecewise 스키마 + 도메인 클리핑 + 열린/닫힌점 마커
5. EquationInput(CodeMirror) 연결 + 파싱 에러 표시
6. 미지 변수 감지 → 파라미터 슬라이더 자동생성
7. LinkBar + `y=t` 드래그 → 전역 `t` 갱신
8. rootFinder로 solution_count 계산, Right 패널에 점 표시
9. Trace On(궤적) 토글
10. ObjectList(대수뷰) 패널
11. 반응형 브레이크포인트 + 모바일 터치 QA
12. 실제 수능 문제(52번, 교점개수 유형)로 엔드투엔드 수동 검증

## Phase 2 — LLM 복붙 문제분석 플로우

**흐름**: 앱에 "문제 분석 프롬프트 복사" 버튼 → 사용자가 자기 LLM(ChatGPT/Claude/Gemini 등)에 문제 이미지 + 프롬프트 입력 → LLM이 고정 포맷으로 출력 → 사용자가 앱에 붙여넣기 → 파싱해서 Left/Right 패널에 자동 적용.

**출력 포맷** (파서가 관대하게 코드펜스/설명 텍스트를 무시하고 파싱):
```json
{
  "top": "piecewise(2*x^3-6*x+1, x<=2; a*(x-2)*(x-b)+9, x>2)",
  "bottom": "solution_count(top(x)=t)",
  "parameter": "t",
  "explanation": "..."
}
```

**UX 안전장치**: 파싱 즉시 그래프를 그리지 않고, "위 함수 / 아래 함수 / 연동 변수"를 미리보기로 보여준 뒤 사용자가 "적용" 눌러야 반영 (LLM이 문제를 잘못 읽었을 경우 수정 기회 제공).

**비용 구조**: 서버에서 LLM API를 호출하지 않으므로 API 비용 없음. LLM 종류에 독립적 — 출력 포맷만 맞으면 어떤 LLM을 쓰든 동일하게 동작.

## Phase 3 — 손그림 → 함수 커브 피팅

기존 조사 결과, "손그림 곡선→함수식" 전용 성숙한 오픈소스는 없음. 대신 도메인이 좁다는 점(y=f(x) 형태, x에 대해 단조로운 함수 그래프)을 활용해 직접 구현.

**파이프라인**:
1. 캔버스에서 스트로크 점 좌표 수집 (터치/마우스)
2. x 기준 리샘플링 + 스무딩 ([curve-fit-nd](https://github.com/ideasman42/curve-fit-nd) 참고 또는 자체 Catmull-Rom)
3. 최소제곱 다항 회귀(1~3차)로 계수 직접 추정
4. 애매한 경우 직선/포물선/삼차/절댓값 꺾임 등 템플릿에 스냅
5. 결과를 Phase 1의 JSON 스키마로 변환해 EquationInput에 반영 (사용자가 확인/수정 가능)

## MVP 범위 밖 (Out of scope)

- 로그인/계정, 서버 사이드 저장 (링크 공유 등은 추후 검토)
- LaTeX WYSIWYG 수식 입력기
- LLM API 직접 연동 (BYOK는 사용자 피드백 보고 추후 검토)

## 리스크

- **rootFinder 정확도**: 샘플링 간격이 너무 크면 근을 놓칠 수 있음 (예: 급격히 변하는 함수). Phase 1 12단계 검증에서 실제 문제로 엣지케이스 확인 필요.
- **Phase 3 정확도**: 다항 회귀가 사용자 의도와 다른 차수로 수렴할 수 있음 — 템플릿 스냅 UI로 보정 기회 제공 필수.
- **모바일 터치 정밀도**: 좁은 화면에서 `y=t` 드래그나 손그림이 부정확할 수 있음 — Phase 1/3 각각에서 별도 QA.
